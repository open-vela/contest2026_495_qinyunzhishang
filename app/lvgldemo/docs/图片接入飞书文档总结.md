## 1. 功能概述

### 1.1 功能定义

本功能在已有"图片上传飞书群聊 + AI回复文字转发群聊"基础上，新增了**飞书云文档写入能力**，实现：

| 功能 | 说明 |
|------|------|
| **语音创建飞书文档** | 用户通过语音指令（如"帮我创建飞书文档《xxx》"）触发AI调用工具，自动在指定云文件夹创建文档 |
| **图片写入文档** | 用户点击"AI分析"后，若存在活跃文档，图片自动写入文档（含标题分组"图片x汇总"） |
| **AI回复写入文档** | AI分析图片的结果及后续多轮对话回复，自动写入当前活跃飞书文档 |
| **动态路由** | 有活跃文档时写入文档，无活跃文档时发送到群聊，两种模式无缝切换 |
| **多轮追加** | 单张图片支持3轮AI问答，多张图片可持续追加到同一文档 |

### 1.2 应用场景对比

```
┌─────────────────────────────────────────────────────────────────┐
│ 模式一：无活跃飞书文档（原始模式）                                 │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  用户点击"AI分析"按钮                                            │
│     ├─ 并行：图片上传到飞书群聊（cam_feishu_thread）             │
│     └─ AI图片分析（WebSocket）                                   │
│           └─ AI回复 → 转发到飞书群聊（feishu_fwd_thread）        │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────────┐
│ 模式二：有活跃飞书文档（文档模式）                                 │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  前提：用户通过语音指令"创建飞书文档《xxx》"已创建文档             │
│                                                                 │
│  用户点击"AI分析"按钮                                            │
│     ├─ 关闭群聊转发（避免文本泄露到群聊）                         │
│     └─ AI图片分析（WebSocket，立即启动，不等待飞书）              │
│           └─ AI回复 → 写入飞书文档（feishu_doc_write_thread）    │
│                 ├─ 第1轮：写"图片x汇总"标题块 + 图片块 + 文字块  │
│                 ├─ 第2轮：追加文字块 + 分割线                    │
│                 └─ 第3轮：追加文字块，结束本轮                    │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

### 1.3 飞书文档 vs 飞书群聊 API 对比

| 维度 | 飞书群聊消息 | 飞书云文档 |
|------|------------|-----------|
| **API域名** | `open.feishu.cn` | `open.feishu.cn` |
| **认证方式** | tenant_access_token | tenant_access_token |
| **图片上传** | `/open-apis/im/v1/images`（multipart） → image_key | `/open-apis/drive/v1/medias/upload_all`（multipart） → file_token |
| **内容写入** | `/open-apis/im/v1/messages`（单条消息） | `/open-apis/docx/v1/documents/{doc_id}/blocks/{block_id}/children`（块结构） |
| **内容格式** | 简单JSON：`{msg_type, content}` | 块树结构：`{children: [{block_type, ...}]}` |
| **排版能力** | 纯文本/图片，无排版 | 支持标题块(5)、文本块(2)、图片块(27)、分割线(22) |
| **可编辑性** | 发送后不可修改 | 创建空块后可PATCH更新内容 |

## 2. 飞书文档API详解

### 2.1 权限要求

文档功能需要在飞书开放平台额外配置以下权限：

| 权限名称 | 权限标识 | 用途 |
|----------|---------|------|
| 查看、评论、编辑和管理云文档 | `docx:document` | 创建文档、读写文档块 |
| 查看、评论、编辑和管理云空间中所有文件 | `drive:drive` | 上传文档内媒体素材 |
| （已有）发送消息 | `im:message` | 群聊模式备用 |

### 2.2 API 1：创建文档

**接口**：`POST /open-apis/docx/v1/documents`

**功能**：在指定云文件夹中创建一个空白文档，返回document_id。

**请求体**：
```json
{
    "title": "图片测试三",
    "folder_token": "fldcnXXXXXXXXXXXX"
}
```

| 参数 | 类型 | 必填 | 说明 |
|------|------|------|------|
| title | string | 否 | 文档标题，最长256字符 |
| folder_token | string | 是 | 目标文件夹token，编译时通过`AGENT_SECRET_FEISHU_DOC_FOLDER_TOKEN`配置 |

**响应体**：
```json
{
    "code": 0,
    "msg": "success",
    "data": {
        "document": {
            "document_id": "doxcnYYYYYYYYYYYY",
            "title": "图片测试三",
            "revision_id": 1
        }
    }
}
```

**关键实现**（[tool_feishu_doc.c:66-203](file:///home/lzw/code/si8658ca/openvela_005_0701/openvela_si8658ca/rtos/packages/ai_agent/src/tools/tool_feishu_doc.c#L66-L203)）：
- 此API由AI Agent作为**工具调用(tool call)**自动触发（非UI直接调用）
- 创建成功后通过回调`feishu_doc_notify_created()`通知上层（voice_assistant）
- 回调设计：避免ai_agent库反向依赖上层应用，通过函数指针解耦

### 2.3 API 2：创建文档块（通用接口）

**接口**：`POST /open-apis/docx/v1/documents/{document_id}/blocks/{block_id}/children`

**功能**：在指定父块下追加子块，支持多种block_type。这是写入文档内容的核心API。

**路径参数**：
| 参数 | 说明 |
|------|------|
| document_id | 文档ID，创建文档时返回 |
| block_id | 父块ID。文档根块ID等于document_id |

**请求体通用结构**：
```json
{
    "children": [
        {
            "block_type": N,
            "<type_specific_obj>": { ... }
        }
    ],
    "index": -1
}
```

**index参数**：-1表示追加到末尾，0表示插入到开头。

### 2.4 各类型Block详细结构

#### 2.4.1 标题块（block_type=5，即heading3）

用于"图片x汇总"分组标识。

**JSON结构**：
```json
{
    "block_type": 5,
    "heading3": {
        "elements": [
            {
                "text_run": {
                    "content": "图片1汇总"
                }
            }
        ],
        "style": {}
    }
}
```

**说明**：
- block_type=3/4/5分别对应heading1/heading2/heading3
- elements数组支持多个text_run片段（可设置不同样式），这里只需纯文本
- style为空对象即可使用默认样式

**实现代码**（[feishu_doc_media.c:260-301](file:///home/lzw/code/si8658ca/openvela_005_0701/openvela_si8658ca/rtos/packages/ai_agent/src/channels/feishu_doc_media.c#L260-L301)）：
```c
int feishu_doc_append_heading1(const char *doc_id, const char *title)
{
    char path[1024];
    snprintf(path, sizeof(path),
        "/open-apis/docx/v1/documents/%s/blocks/%s/children", doc_id, doc_id);

    cJSON *root = cJSON_CreateObject();
    cJSON *children = cJSON_AddArrayToObject(root, "children");
    cJSON *block = cJSON_CreateObject();
    cJSON_AddNumberToObject(block, "block_type", 5);

    cJSON *heading = cJSON_AddObjectToObject(block, "heading3");
    cJSON *elements = cJSON_AddArrayToObject(heading, "elements");
    cJSON *elem = cJSON_CreateObject();
    cJSON *tr = cJSON_AddObjectToObject(elem, "text_run");
    cJSON_AddStringToObject(tr, "content", title);
    cJSON_AddItemToArray(elements, elem);
    cJSON_AddObjectToObject(heading, "style");

    cJSON_AddItemToArray(children, block);
    // ... POST请求 ...
}
```

#### 2.4.2 文本块（block_type=2，即text/paragraph）

用于写入AI回复文字内容。

**JSON结构**：
```json
{
    "block_type": 2,
    "text": {
        "elements": [
            {
                "text_run": {
                    "content": "AI：这是一张桌面照片..."
                }
            }
        ],
        "style": {}
    }
}
```

**多行文本处理**：飞书文本块内的text_run不支持`\n`换行，需要按`\n`分割，每行创建一个独立的text block。实现中使用`strtok_r`按行分割，跳过空行（飞书拒绝空content）。

**实现代码**（[feishu_doc_media.c:303-369](file:///home/lzw/code/si8658ca/openvela_005_0701/openvela_si8658ca/rtos/packages/ai_agent/src/channels/feishu_doc_media.c#L303-L369)）。

#### 2.4.3 图片块（block_type=27）

图片写入采用**三步法**（先创建空块 → 上传媒体 → PATCH绑定token），不能一步完成。

**第一步：创建空图片块（POST）**
```json

    "block_type": 27,
    "image": {
        "width": 600,
        "height": 400

```

**响应**：
```json
{
    "code": 0,
    "data": {
        "children": [
            {
                "block_id": "doxcnBLOCKXXXXXX",

            }

}
```

### 2.5 API 3：上传文档媒体素材

**接口**：`POST /open-apis/drive/v1/medias/upload_all`

**功能**：上传图片二进制数据到飞书云盘，返回file_token（不同于群聊图片的image_key）。

**Content-Type**：`multipart/form-data`，包含以下字段：

| 字段名 | 类型 | 说明 |
|--------|------|------|
| file_name | string | 文件名，如"doc_image.jpg" |
| parent_type | string | 固定值"docx_image"，表示文档内图片 |
| parent_node | string | 图片块的block_id（第一步创建的空块ID） |
| size | string | 文件大小（字节数，字符串形式） |
| extra | string | JSON字符串：`{"drive_route_token":"<doc_id>"}` |
| file | binary | 图片二进制数据，Content-Type: image/jpeg |

**响应体**：
```json
{
    "code": 0,
    "data": {
        "file_token": "DnCxxxxxxxxxxxxxxxxxxxxxx"
    }
}
```

**multipart构造要点**（[feishu_doc_media.c:51-101](file:///home/lzw/code/si8658ca/openvela_005_0701/openvela_si8658ca/rtos/packages/ai_agent/src/channels/feishu_doc_media.c#L51-L101)）：
- extra字段必须包含drive_route_token，值为文档ID
- parent_node为第一步创建的空图片块block_id
- size字段为字符串形式的文件大小

### 2.6 API 4：PATCH更新图片块（绑定file_token）

**接口**：`PATCH /open-apis/docx/v1/documents/{document_id}/blocks/{block_id}?update_image_elements=replace_image`

**功能**：将上传后获得的file_token绑定到之前创建的空图片块，完成图片显示。

**请求体**：
```json
{
    "replace_image": {
        "token": "DnCxxxxxxxxxxxxxxxxxxxxxx"
    }
}
```

**⚠️ 注意**：
- token字段直接是file_token字符串，**不是**嵌套对象（如`{"token": {"file_token": "xxx"}}`会报错）
- 查询参数`update_image_elements=replace_image`必须带上

**实现代码**（[feishu_doc_media.c:476-503](file:///home/lzw/code/si8658ca/openvela_005_0701/openvela_si8658ca/rtos/packages/ai_agent/src/channels/feishu_doc_media.c#L476-L503)）。

### 2.7 图片写入三步法完整流程

```
POST /docx/v1/documents/{doc_id}/blocks/{doc_id}/children
  body: {block_type:27, image:{width:600,height:400}}
  → 返回 image_block_id
       │
       ▼
POST /drive/v1/medias/upload_all (multipart/form-data)
  parent_node = image_block_id
  extra = {"drive_route_token": doc_id}
  → 返回 file_token
       │
       ▼
PATCH /docx/v1/documents/{doc_id}/blocks/{image_block_id}?update_image_elements=replace_image
  body: {replace_image:{token: file_token}}
  → 图片显示成功
```

**封装接口**：`feishu_doc_append_image()`一键完成三步（[feishu_doc_media.c:505-538](file:///home/lzw/code/si8658ca/openvela_005_0701/openvela_si8658ca/rtos/packages/ai_agent/src/channels/feishu_doc_media.c#L505-L538)）。

## 4. 文档创建流程

### 4.1 触发方式

文档创建**不由UI按钮直接触发**，而是通过AI工具调用（function calling）机制：

1. 用户语音："小Q小Q，帮我创建飞书文档《图片测试三》"
2. 语音通过WebSocket发送到云端大模型
3. 大模型识别意图，返回tool_call指令，调用`feishu_doc_create`工具
4. ai_agent核心层执行`tool_feishu_doc_create_execute()`
5. 调用飞书API创建文档，成功后通过回调通知上层

### 4.2 回调链路

```c
// tool_feishu_doc.c - 工具执行成功后
feishu_doc_notify_created(doc_id_str, doc_title_str);
  ↓
// feishu_doc_media.c - 回调分发
if (s_doc_created_cb) {
    s_doc_created_cb(doc_id, title, s_doc_created_cb_userdata);
}
  ↓
// voice_assistant.c - 上层注册的回调
static void feishu_doc_created_callback(const char *doc_id, const char *title, void *user_data)
{
    voice_assistant_set_active_feishu_doc(doc_id, title);
}
  ↓
// voice_assistant_set_active_feishu_doc:
//   1. 加锁写入s_active_feishu_doc_id
//   2. s_doc_image_count = 0（重置图片计数）
//   3. s_need_skip_doc_prefix = true（下次AI回复需截断前缀）
//   4. s_last_user_question[0] = '\0'
```

### 4.3 工具注册

文档相关工具在`tool_registry.c`中注册到AI Agent工具表，大模型可自动识别并调用：
- `feishu_doc_create`：创建文档（参数：title、folder_token）
- `feishu_doc_write`：向文档追加内容（参数：document_id、content）
- `feishu_doc_read`：读取文档内容（参数：document_id）
- `feishu_doc_list`：列出文件夹下文档（参数：folder_token）

## 5. 图片写入文档完整流程

### 5.1 图片写入触发条件

图片写入发生在**第1轮AI回复到达时**（即AI完成图片分析后返回第一张描述时），不是点击按钮时立即上传。

**原因**：
- 文档写入需要知道目标doc_id（文档可能在点击按钮之后才通过语音创建）
- 第1轮AI回复同时携带图片描述文字，图片和文字需要一起排版
- 与群聊模式不同（群聊是点击按钮即上传图片到IM），文档模式由AI回复触发

### 5.2 图片写入时序

```
用户点击"AI分析"
     │
     ├─ voice_assistant_analyze_image()  立即启动AI分析（不等待飞书）
     ├─ voice_assistant_has_active_feishu_doc() 检查是否有活跃文档
     │     ├─ 有文档: voice_assistant_disable_feishu_forward() 关闭群聊转发
     │     └─ 无文档: cam_send_to_feishu_async() 并行上传图片到群聊
     │
     ▼
（等待AI WebSocket返回）
     │
     ▼
AI文本回复到达（第1轮，含图片描述）
     │
     ├─ feishu_doc_write_dispatch(image_path, ai_text, user_question)
     │     │
     │     ├─ 检查s_active_feishu_doc_id非空
     │     ├─ round = s_fwd_ai_count = 1
     │     ├─ malloc(doc_write_arg_t)，填充参数
     │     └─ pthread_create(feishu_doc_write_thread)
     │
     ▼
feishu_doc_write_thread（后台线程）
     │
     ├─ [round==1] s_doc_image_count++ → "图片1汇总"
     ├─ feishu_doc_append_heading1(doc_id, "图片1汇总")  → 创建标题块(block_type=5)
     ├─ feishu_doc_append_image(doc_id, image_path)     → 三步法写入图片
     │     ├─ feishu_doc_create_image_block()           → 创建空图片块
     │     ├─ feishu_doc_upload_image_media()           → 上传媒体文件
     │     └─ feishu_doc_patch_image_block()            → PATCH绑定token
     ├─ strip_doc_create_prefix(ai_text)                → 截断文档创建前缀
     ├─ 构造"我：xxx\nAI：xxx"格式文本
     ├─ feishu_doc_append_text(doc_id, full_content)    → 创建文本块(block_type=2)
     └─ feishu_doc_append_divider(doc_id)               → 创建分割线(block_type=22)（非最后一轮）
```

## 6. AI回复文字写入文档流程

### 6.1 文本分发逻辑

AI回复文本到达WebSocket接收线程后，根据当前状态走两条路径：

```c
// voice_assistant.c - WS接收线程中
if (s_fwd_enabled && s_fwd_receive_id[0] && s_fwd_ai_count < FEISHU_FWD_MAX_AI_REPLIES) {
    feishu_fwd_dispatch(prefix, content);  // 路径1：群聊转发
}

if (s_active_feishu_doc_id[0]) {
    feishu_doc_write_dispatch(s_img_ctx.filename, content, user_question);  // 路径2：文档写入
}
```

两条路径**可以同时存在吗**？正常流程不会：
- 无文档时：`cam_ai_btn_cb`中启动`cam_send_to_feishu_async`，上传成功后`cam_feishu_done_cb`开启`s_fwd_enabled`
- 有文档时：`cam_ai_btn_cb`中调用`voice_assistant_disable_feishu_forward()`关闭s_fwd_enabled

但`s_fwd_img_analysis_started`是独立的，确保文档写入的轮次计数正确。

### 6.2 前缀截断处理（strip_doc_create_prefix）

AI在创建文档后，LLM会返回类似以下的确认文本：

```
"好的，正在为您创建飞书文档《图片测试三》，请稍等。这是一张桌面照片..."
```

写入文档时，"好的...请稍等。"这段是给用户看的操作确认，不应写入文档正文，需要截断。

**截断前缀匹配模式**：
```c
// 跳过开头空白和标点
// 匹配"好的[，,]正在为你创建飞书文档"，跳过直到遇到句号/感叹号
// "好的，正在为你创建飞书文档"xxx"，请稍等。" → 跳过到句号之后
```

### 6.3 UTF-8中文字符处理要点

这是开发中踩过的坑（详见第11章问题#6），核心原则：

1. **中文字符在UTF-8中占3字节**，不能用硬编码字节数
2. **中文标点（，。！）也占3字节**，不能用`*p == '，'`这种单字节比较
3. **正确做法**：使用`sizeof("中文串")-1`获取正确字节数，用`strncmp`比较

```c
// ❌ 错误写法（硬编码字节数，导致乱码）
strncmp(p, "好的", 2)     // "好的"=6字节，只比2字节 → 截断"好"字
strncmp(p, "，", 1)       // "，"=3字节，只比1字节
*p == '，'               // 多字节字符常量，C语言中行为未定义

// ✅ 正确写法
strncmp(p, "好的", sizeof("好的")-1)    // 6字节
strncmp(p, "，", sizeof("，")-1)        // 3字节
strncmp(p, "。", sizeof("。")-1) == 0   // 正确匹配中文句号
```

### 6.4 聊天格式拼接

文档中的文本采用与飞书聊天一致的格式：

- 有用户问题时：`"我：{问题}\nAI：{回复}"`
- 无用户问题（第1轮拍照自动触发无语音问题）：`"AI：{回复}"`

拼接使用纯`memcpy`（避免`sprintf`对`%`等特殊字符的解析问题）：
```c
full_content = malloc(user_prefix_len + user_q_len + newline_len + ai_prefix_len + ai_text_len + 1);
char *p = full_content;
memcpy(p, user_prefix, user_prefix_len); p += user_prefix_len;
memcpy(p, a->user_question, user_q_len); p += user_q_len;
memcpy(p, newline, newline_len); p += newline_len;
memcpy(p, ai_prefix, ai_prefix_len); p += ai_prefix_len;
memcpy(p, clean_ai_text, ai_text_len); p += ai_text_len;
*p = '\0';
```

## 7. 文档写入线程实现细节

### 7.1 线程参数结构体

```c
typedef struct {
    char doc_id[128];          // 目标文档ID
    char ai_text[4096];        // AI回复文本（截断前缀后的干净文本）
    char image_path[128];      // 图片路径（仅round=1有效）
    char user_question[256];   // 用户问题（语音识别结果，空串表示无问题）
    int round;                 // 轮次：1/2/3
} doc_write_arg_t;
```

线程创建时堆分配参数，线程结束时自己free。

### 7.2 线程栈大小

文档写入线程栈大小设为**64KB**（群聊上传线程为128KB），因为文档写入不需要TLS握手（TLS连接复用）和大文件读取（图片读取在独立函数内分配/释放）。

```c
pthread_attr_setstacksize(&attr, 64 * 1024);
pthread_attr_setdetachstate(&attr, PTHREAD_CREATE_DETACHED);
```

### 7.3 轮次逻辑与状态管理

```c
// 第1轮：图片 + 文字 + 分割线
if (a->round == 1 && a->image_path[0] != '\0') {
    s_doc_image_count++;
    feishu_doc_append_heading1(doc_id, heading_title);
    feishu_doc_append_image(doc_id, a->image_path);
}
feishu_doc_append_text(doc_id, full_content);

// 非最后一轮追加分割线
if (a->round < FEISHU_FWD_MAX_AI_REPLIES) {
    feishu_doc_append_divider(a->doc_id);
}

// 第3轮完成后的状态清理
if (a->round >= FEISHU_FWD_MAX_AI_REPLIES) {
    s_fwd_img_analysis_started = false;     // 结束本轮图片分析流程
    s_last_user_question[0] = '\0';         // 清空用户问题缓存
    // 注意：不清空s_active_feishu_doc_id！允许多张图片追加到同一文档
}
```

**重要设计决策**：3轮问答完成后**不清空活跃文档ID**，这样用户可以继续拍照，新的图片会继续追加到同一文档（图片编号继续递增：图片4汇总、图片5汇总...），直到用户创建新文档时`voice_assistant_set_active_feishu_doc`才会覆盖doc_id并重置计数。

### 8.3 业务流程演进

此逻辑经历了**三次调整**：

| 版本 | 流程 | 用户等待时间 |

## 11. 开发过程中遇到的问题与解决方案

### 问题1：通过语音创建飞书文档后滑动到camera界面卡住数秒

**现象**：语音创建文档成功后，手势滑动切换到camera页面，界面卡住3~5秒才响应。

**根因分析**：
1. **TTS线程无效重试**：默认语音配置"Tina"对qwen3-tts-flash-realtime模型无效，导致pool TTS连接失败后无条件fallback到direct TTS，重试多次占用CPU
2. **TCP connect无超时**：`mbedtls_net_connect`使用阻塞connect，网络异常时默认75秒超时，TTS失败重连时长时间阻塞
3. **页面创建同步阻塞**：屏幕切换时在LVGL主线程同步调用`create_camera_page()`，创建过程中的资源初始化阻塞UI

**修复方案**：

| 修复点 | 文件 | 改动 |
|--------|------|------|
| 默认语音改为Cherry | agent_config.h | `VOICE_NAME_DEFAULT "Cherry"`替代"Tina" |
| TCP connect 5秒超时 | ws_conn_pool.c, dashscope_tts.c | 非阻塞socket+select实现connect超时控制 |
| 协议错误不重试 | voice_tts.c | -EPROTO错误时直接返回，不再fallback到direct TTS |
| 异步创建页面 | lvgldemo.c | 通过`lvgl_dispatch_async`异步调度camera页面创建 |

### 问题2：TTS长时间卡住（~18秒）

**现象**：唤醒后TTS不播放，等待约18秒后才有声音或报错。

**根因**：上述问题1的子问题，TTS无效重试+无超时叠加导致长时间阻塞。修复同问题1，TTS阻塞时间缩短至5秒内（connect超时时间）。

### 问题3：有活跃飞书文档时AI回复文本仍然转发到群聊

**现象**：创建文档后点击AI分析，AI回复同时出现在文档和群聊中。

**根因**：`s_fwd_enabled`是静态变量，上一次无文档模式下设为true后，切换到文档模式时没有被关闭。群聊上传线程`cam_feishu_thread`在无文档时不会启动（因为有文档时跳过了`cam_send_to_feishu_async`），所以不会重新设置s_fwd_enabled，但旧值true仍然残留。

**修复**：
1. 新增`voice_assistant_disable_feishu_forward()`接口
2. 在`cam_ai_btn_cb`中，检测到有活跃文档时主动调用该接口关闭转发
3. 该接口只关闭`s_fwd_enabled`，不清零文档相关状态，不影响文档写入流程

### 问题4：图片块创建API返回400错误

**现象**：调用创建图片块API时返回400 Bad Request。

**根因**：创建空图片块时在image对象中传了空字符串的file_token字段：
```c
// ❌ 错误
cJSON *image = cJSON_AddObjectToObject(block, "image");
cJSON_AddStringToObject(image, "token", "");  // 传空token导致400
cJSON_AddNumberToObject(image, "width", 600);
```

**修复**：创建空块时不传file_token/token字段，只传width/height：
```c
// ✅ 正确
cJSON *image = cJSON_AddObjectToObject(block, "image");
cJSON_AddNumberToObject(image, "width", 600);
cJSON_AddNumberToObject(image, "height", 400);
```

file_token在第三步PATCH时再绑定。

### 问题5：PATCH图片块API格式错误

**现象**：上传媒体成功获得file_token后，PATCH请求报错。

**根因**：replace_image的token字段格式有误，错误地嵌套了一层对象：
```c
// ❌ 错误
cJSON *token_obj = cJSON_AddObjectToObject(update, "token");
cJSON_AddStringToObject(token_obj, "file_token", file_token);
// 结果：{"replace_image":{"token":{"file_token":"xxx"}}}
```

**修复**：token直接是字符串值：
```c
// ✅ 正确
cJSON_AddStringToObject(update, "token", file_token);
// 结果：{"replace_image":{"token":"DnCxxxxxx"}}
```

### 问题6：AI回复中"好"字乱码（UTF-8截断问题）

**现象**：创建文档后，AI回复中"好"字显示为`�`（UTF-8替换字符）。

**用户原始反馈**：
```
AI：�的，正在为您创建飞书文档《图片测试三》。
AI：这是一张桌面照片，前景有一个蓝色笑脸的小机器人玩偶...
```

**根因分析**：

`strip_doc_create_prefix`函数中3处使用了**硬编码字节数**的`strncmp`，但中文字符在UTF-8中占3字节：

| 原代码 | 问题 | 实际后果 |
|--------|------|---------|
| `strncmp(p, "好的", 2)` | "好的"是6字节（好=E5A5BD，的=E79A84），只比较2字节(E5A5)后`p+=2` | 指针停在"好"的第3字节(BD)，后续输出从BD开始→非法UTF-8序列→显示`�` |
| `strncmp(p, "，", 1)` | "，"是3字节（EFBC8C），只比1字节 | 可能误匹配其他UTF-8字符的首字节EF |
| `strncmp(p, "正在为你创建飞书文档", 10)` | 10个中文字×3=30字节，只比10字节 | 只匹配了前3个多字的首字节部分 |

另外3处while循环中使用了`*p == '，'`这种多字节字符常量与单字节char比较，在C语言中属于未定义行为（`'，'`是多字节字符常量，值为实现定义的整数），永远不会匹配，导致中文标点无法正确跳过。

**修复**：全部改用`sizeof("中文字符串")-1`获取正确的UTF-8字节数：

```c
// 修复前
while (*p == ' ' || *p == ',' || ... || *p == '，' || *p == '。') { ... }
if (strncmp(p, "好的", 2) == 0) p += 2;
if (strncmp(p, "，", 1) == 0) p += 1;

// 修复后
while (*p == ' ' || *p == ',' || *p == '.' || *p == '\n' ||
       strncmp(p, "，", sizeof("，")-1) == 0 ||
       strncmp(p, "。", sizeof("。")-1) == 0) {
    if (*p == ' ' || *p == ',' || *p == '.' || *p == '\n') p++;
    else if (strncmp(p, "，", sizeof("，")-1) == 0) p += sizeof("，")-1;
    else if (strncmp(p, "。", sizeof("。")-1) == 0) p += sizeof("。")-1;
}
if (strncmp(p, "好的", sizeof("好的")-1) == 0) p += sizeof("好的")-1;
```

**可能受影响的其他字符**：所有被前缀匹配逻辑处理的中文字符都可能受影响，实际触发乱码的是前缀开头的"好"字。修复后所有中文匹配均使用正确字节数，不会再有类似乱码。

### 问题7：AI分析按钮点击后用户等待时间过长

**现象**：点击AI分析按钮后，用户需要等待8秒以上才能看到AI结果。

**根因**：初版流程是"先上传图片到飞书（~3秒），上传成功回调中再启动AI分析（~5秒）"，串行执行导致等待时间叠加。

**修复方案演进**：
1. v2优化：将AI分析提前到按钮点击时立即启动，图片上传并行执行
2. v3优化：有活跃文档时跳过群聊图片上传（文档写入线程会自己处理图片），减少不必要的网络请求
3. 最终效果：点击按钮后AI立即开始分析，用户等待时间从8秒缩短至5秒（纯AI分析时间）
