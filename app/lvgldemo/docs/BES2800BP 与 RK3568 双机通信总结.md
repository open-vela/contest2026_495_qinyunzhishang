## 1. 整体架构概述

### 1.1 设备角色定位

| 设备 | 角色 | 操作系统 | 主控芯片 | 职责 |
|------|------|----------|----------|------|
| **BES2800BP 开发板** | SPI 从机 + UART 通信端 | NuttX RTOS | BES2800BP | 业务主控：UI 显示、用户交互、发起拍照命令、接收并显示照片 |
| **Lubancat 2N 开发板** | SPI 主机 + UART 通信端 | Linux | RK3568 | 执行端：接收拍照命令、控制摄像头拍照、生成缩略图、通过 SPI 发送图像数据 |

**接口分工设计考量**：

- **UART（控制通道）**：传输命令帧和确认帧，数据量小、可靠性要求高。UART 是全双工、异步通信，适合传输控制信令。波特率 921600 bps 足够满足命令交互的实时性需求。
- **SPI（数据通道）**：传输图像数据（缩略图约 88KB，原图约 1.2MB），数据量大、需要高速传输。SPI 是同步通信，由主机提供时钟，可达 24MHz，适合大数据量传输。

## 2. 通信流程分析

### 2.1 启动阶段：初始化与链路建立

#### 2.1.1 2800 侧初始化流程

2800 侧的初始化分为**两个阶段**：板级启动阶段（设备注册，DMA 未启动）和应用启动阶段（打开设备，DMA 启动）。

##### 阶段 A：板级启动（设备注册，DMA 未启动）

系统上电后，NuttX 启动流程会依次执行板级初始化函数，最终将 SPI 从机注册为字符设备 `/dev/spislv0`，但此时 **DMA 尚未启动**，仅完成硬件资源分配和设备注册。

```
[上电]
  │
  ├─ bes_spi_driver_prob()                              [boards/common/src/bes_spi.c]
  │    作用：板级 SPI 设备探测入口，由 NuttX 启动流程调用
  │    └─ board_spislavedev_initialize(0)               [boards/common/src/bes_board_spi_slave.c]
  │         作用：初始化 SPI0 从机设备并注册字符设备
  │         ├─ bes_spislave_initialize(bus=0)           [chips/bes/bes_spi_slave.c]
  │         │    作用：分配并初始化 SPI 从机私有结构体，配置引脚
  │         │    ├─ bes_spi_pincontrol(port, true)
  │         │    │    作用：配置 IOMUX，将物理引脚切换到 SPI 功能
  │         │    │    └─ hal_iomux_set_spi_slave()
  │         │    │         作用：设置 MOSI/MISO/SCLK/CS 引脚为 SPI 从机功能
  │         │    ├─ 初始化 priv 结构体成员：
  │         │    │    ├─ nbits = 8                    // 数据位宽 8 bit
  │         │    │    ├─ mode = SPISLAVE_MODE0        // SPI Mode 0 (CPOL=0, CPHA=0)
  │         │    │    ├─ cfg.slave = true             // 从机模式
  │         │    │    ├─ rx_dma_length = 4096          // DMA 缓冲区大小 (SPI_SLAVE_BUFSIZE)
  │         │    │    ├─ rx_dma_buffer = memalign(32, 4096)
  │         │    │    │    作用：分配 32 字节对齐的 DMA 接收缓冲区（DMA 对齐要求）
  │         │    │    └─ tx_dma_buffer = memalign(32, 4096)
  │         │    ├─ nxsem_init(&exclsem, 0, 1)         // ★ 互斥信号量，见下方详解
  │         │    ├─ nxsem_init(&wait, 0, 0)            // 同步信号量，初始值 0
  │         │    │    作用：用于 read() 阻塞等待，RX_COMPLETE 时 post 唤醒
  │         │    └─ nxsem_init(&dmasem, 0, 0)          // DMA 完成同步信号量
  │         └─ spi_slave_register(ctrlr, bus=0)        [rtos/nuttx/drivers/spi/spi_slave_driver.c]
  │              作用：将 SPI 从机注册为字符设备 /dev/spislv0
  │              └─ register_driver("/dev/spislv0", &g_spislavefops, ...)
  │
  └─ [此时 /dev/spislv0 已存在，但 DMA 未启动，无法收发数据]
```

**`nxsem_init(&exclsem, 0, 1)` 详解**：

这是 NuttX 的信号量初始化函数（`nx` 前缀 = NuttX，`sem` = semaphore），三个参数含义：

| 参数 | 值 | 含义 |
|------|-----|------|
| `&exclsem` | 信号量地址 | 指向 `bes_spislavedev_s` 结构体中的 `sem_t exclsem` 成员 |
| `0` | pshared | 0 = 线程间共享（非进程间） |
| `1` | 初始值 | **初始值 1 使其表现为互斥锁** |

**为什么初始值 1 就是互斥锁**：信号量本质是计数器，`nxsem_wait` 减 1（为 0 时阻塞），`nxsem_post` 加 1（唤醒等待线程）。初始值 1 意味着同一时刻只允许 1 个线程持有，实现互斥访问。

**`exclsem` 的实际作用**：保护 SPI 总线互斥访问。在 `spi_lock()` 函数中使用：

```c
static int spi_lock(FAR struct spi_slave_ctrlr_s *dev, bool lock)
{
    if (lock)
        return nxsem_wait_uninterruptible(&priv->exclsem);  // 加锁
    else
        return nxsem_post(&priv->exclsem);                  // 解锁
}
```

场景：多个线程可能同时操作同一个 SPI 控制器（如应用线程发数据 + 中断线程收数据），`exclsem` 确保同一时刻只有一个线程操作 SPI 寄存器/DMA，防止配置冲突。

**`nxsem_init(&wait, 0, 0)` 详解**：

`wait` 信号量初始值为 0，用于 **`read()` 阻塞等待数据**。当应用调用 `read(/dev/spislv0)` 时，驱动内部 `nxsem_wait(&wait)` 阻塞；当 DMA 接收完成（RX_COMPLETE）时，LHF 调用 `SPIS_DEV_NOTIFY` → `nxsem_post(&wait)` 唤醒应用读取数据。这是典型的生产者-消费者同步模型。

##### 阶段 B：应用启动（打开设备，DMA 启动）

LVGL 应用启动后，`create_camera_page()` 被调用，此时打开 `/dev/spislv0` 会触发首次 `bind`，**DMA 在此刻启动**，开始等待 2N 发送数据。

```
[LVGL 应用启动]
  │
  └─ create_camera_page(parent)                         [rtos/apps/examples/lvgldemo/camera_page.c]
       作用：创建 Camera 页面 UI，打开 UART/SPI 设备，启动接收线程
       │
       ├─ 创建 UI 界面（预览区 280x280、状态标签、拍照/获取按钮）
       │
       ├─ cam_uart_fd = cam_uart_open()                 // 打开 /dev/ttyS1
       │    作用：打开 UART 设备并配置为 raw mode
       │    ├─ open("/dev/ttyS1", O_RDWR | O_NOCTTY)
       │    ├─ cfsetispeed/cfsetospeed(B921600)        // 设置波特率 921600
       │    ├─ tio.c_cflag |= CS8 | CLOCAL | CREAD     // 8N1，无流控
       │    ├─ tio.c_lflag &= ~(ICANON | ECHO | ISIG)  // raw mode
       │    └─ tcflush(fd, TCIOFLUSH)                   // 清空缓冲区
       │
       ├─ pthread_create(cam_uart_rx_thread)            // 启动 UART 接收线程
       │    作用：状态机解析 UART 帧，处理 CAPTURE_ACK/GET_IMAGE_ACK 等
       │
       ├─ cam_spi_fd = open("/dev/spislv0", O_RDWR)     // ★ 打开 SPI 从机设备
       │    │
       │    └─ [内核] spi_slave_open()                  [spi_slave_driver.c]
       │         作用：首次打开时（crefs==0）自动触发 bind
       │         ├─ nxmutex_lock(&priv->lock)           // 获取驱动锁
       │         ├─ if (priv->crefs == 0):
       │         │    └─ SPIS_CTRLR_BIND(priv->ctrlr, priv, MODE0, 8)
       │         │         └─ spislave_bind()           [bes_spi_slave.c]
       │         │              作用：绑定设备，打开 HAL，★启动首次 DMA
       │         │              ├─ priv->dev = dev
       │         │              ├─ spislave_setmode(MODE0)   // 配置 SPI 模式
       │         │              ├─ spislave_setbits(8)        // 配置位宽
       │         │              ├─ hal_user_spi_open(port, &cfg)
       │         │              │    作用：打开 SPI HAL，配置 SPI 控制器寄存器
       │         │              └─ schedule_transfer(priv, SCHEDULE)
       │         │                   作用：调度传输，启动首次 RX DMA（见 §2.1.2 详解）
       │         └─ priv->crefs++
       │
       └─ pthread_create(cam_spi_rx_thread)             // 启动 SPI 接收线程
            作用：poll/read SPI 数据，解析帧，发送 bitmap ACK
```

> **重要结论**：**Camera 页面创建时（即应用启动时），SPI DMA 就已经启动并等待 2N 传输数据了**。这是通过 `open("/dev/spislv0")` 触发 `spislave_bind()` → `schedule_transfer(SCHEDULE)` → `spislave_prepare_next_rx()` 实现的。用户无需先点拍照，DMA 就已就绪。但应用层通过 `cam_spi_recv_active` 标志控制是否真正处理接收到的数据——只有发出 `SPI_READY` 后才置为 true，开始解析帧。

#### 2.1.2 SPI DMA 预启动详解（小白友好版）

SPI 从机的 DMA 接收必须**在主机拉低 CS 之前就启动**，否则数据会丢失。整个预启动过程如下：

```
spislave_bind() 中调用 schedule_transfer(priv, SCHEDULE)
  │
  ▼
schedule_transfer(SCHEDULE)                            [bes_spi_slave.c]
  作用：调度传输的核心函数，根据 action 决定启动 RX 还是 TX
  │
  ├─ enter_critical_section()                          // 关中断，保护临界区
  │    作用：防止 DMA 启动过程被中断打断
  │
  ├─ [SCHEDULE action 不走 TX_DONE/RX_DONE 分支，直接准备 RX]
  │
  ├─ spislave_prepare_next_rx(priv)                    // ★ 准备下一次 RX
  │    作用：清空缓冲区，启动 DMA，使能 CS 中断
  │    │
  │    ├─ is_rx_processing = true                      // 标记 RX 正在进行
  │    ├─ rx_length = 0                                // 清空接收长度计数
  │    ├─ memset(rx_dma_buffer, 0, rx_dma_length)      // 清空 DMA 缓冲区
  │    │    作用：防止历史数据污染，确保 trans_len 计算准确
  │    │
  │    ├─ spislave_cs_irq_enable()                     // ★ 使能 CS 上升沿中断
  │    │    作用：当主机拉高 CS（传输结束）时触发中断
  │    │    ├─ bes_io_ioexpander_initialize()          // 获取 IOExpander
  │    │    └─ IOEXP_SETOPTION(..., IOEXPANDER_VAL_RISING)
  │    │         作用：配置 CS 引脚为上升沿中断触发
  │    │
  │    └─ spi_dmarecvblock(priv, rx_dma_buffer, rx_dma_length)
  │         作用：启动 DMA 接收，等待主机数据
  │         └─ spi_dmaexchange(NULL, rx_dma_buffer, 4096)
  │              作用：DMA 交换函数
  │              └─ hal_user_spi_dma_recv(port, rx_dma_buffer, 4096)
  │                   作用：★ HAL 层启动 DMA，SPI 控制器开始监听 MOSI
  │                   [此时 DMA 已就绪，任何 MOSI 数据都会被自动写入 rx_dma_buffer]
  │
  └─ leave_critical_section()                          // 开中断
```

**预启动后的状态**：
- `is_rx_processing = true`：标记 DMA 正在运行
- `rx_dma_buffer` 已清零，等待数据写入
- CS 上升沿中断已使能：主机拉高 CS 时会触发 `cs_interrupt_handler()`
- DMA 硬件就绪：任何 MOSI 上的数据都会被自动接收

**为什么必须预启动**：SPI 是同步通信，从机被动接收，没有"请求"机制。如果 DMA 没在 CS 拉低前启动，主机发送的数据会丢失（SPI 控制器收到数据但 DMA 无人读取，数据被覆盖）。

#### 2.1.3 2N 侧初始化流程

```
[用户启动脚本]
  │
  └─ python3 camera_hub_2n.py [speed] [mode]
       │
       ├─ check_uart_baudrate()                        // 检查并设置波特率

       │

```

#### 2.1.4 链路建立完成标志

- **2800 侧**：UART RX 线程启动、SPI 设备已打开且 **DMA 已预启动**（等待数据）
- **2N 侧**：UART 已打开、波特率已验证、ACK 读取线程已启动
- 此时双向通信链路已建立，等待用户触发业务流程

### 2.2 业务运行阶段：数据交互机制

> **重要**：当前协议采用**末尾 Bitmap 汇总校验机制**（非每帧校验）。2N 连续发送所有数据帧 + END 帧，2800 收到 END 后用 bitmap 精确指示缺失帧，2N 仅重传缺失帧。详见 §4 和 [SPI校验机制演进总结.md](file:///home/lzw/code/si8658ca/openvela_003_0623/openvela_si8658ca/doc/SPI校验机制演进总结.md)。

#### 2.2.2 SPI 通信主机（2N）详细运行过程

**末尾汇总校验发送流程**：

```
spi_send_image() [camera_hub_2n.py]
  │
  ├─ max_attempts = 3
  │
  ├─ for attempt in range(max_attempts):
  │    │
  │    ├─ [第一轮：连续发送所有数据帧]
  │    │   offset = 0
  │    │   while offset < total:
  │    │       chunk = data[offset:offset+256]
  │    │       frame = build_spi_frame(type, sid, total, offset, chunk)
  │    │       │
  │    │       └─ 构造帧: magic(4) + type(1) + session(4) + total(4)
  │    │                   + offset(4) + len(2) + data(256) + crc(2) = 277 字节
  │    │
  │    │       spi.xfer2(list(frame))           // ★ SPI 传输
  │    │       │
  │    │       └─ [Linux 内核 spidev 驱动]
  │    │            ├─ 构建 spi_transfer 结构
  │    │            ├─ spi_sync()
  │    │            │    └─ mxc_spi_transfer_one()
  │    │            │         ├─ mxc_spi_configure()     // 配置 SCLK、模式
  │    │            │         ├─ gpio_set_value(CS, 0)   // ★ CS 拉低
  │    │            │         ├─ dma_async_issue_pending() // 启动 DMA
  │    │            │         │    └─ 逐字节: SCLK 上升沿 → MOSI 数据有效
  │    │            │         ├─ wait_for_completion()   // 等待 DMA 完成
  │    │            │         └─ gpio_set_value(CS, 1)   // ★ CS 拉高
  │    │            └─ 返回传输字节数
  │    │
  │    │       offset += len(chunk)
  │    │       time.sleep(0.003)              // 帧间延时 3ms
  │    │
  │    ├─ [发送 END 帧]
  │    │   end_frame = build_spi_frame(type_end, sid, total, total, b"")
  │    │   spi.xfer2(list(end_frame))
  │    │
  │    ├─ [等待 Bitmap ACK]
  │    │   ok, ack_off, missing = wait_bitmap_ack(session_id, timeout=3.0)
  │    │   │
  │    │   └─ ack_queue.get() 从后台线程获取 ACK
  │    │
  │    ├─ if ok:
  │    │   └─ return True                    // 传输完成
  │    │
  │    ├─ if missing is None:
  │    │   └─ ACK 超时，重试
  │    │
  │    └─ [有缺失帧：选择性重传]
  │       _send_frames_by_offsets(spi, data, sid, type, missing)
  │       │
  │       ├─ for offset in missing:          // 仅重传缺失的帧
  │       │   chunk = data[offset:offset+256]
  │       │   frame = build_spi_frame(type, sid, total, offset, chunk)
  │       │   spi.xfer2(list(frame))
  │       │   time.sleep(0.003)
  │       │
  │       ├─ 发送 END 帧
  │       └─ 等待下一次 bitmap ACK
  │           if missing2 为空: return True
  │
  └─ return False                           // 3 次重试后仍失败
```

#### 2.2.4 关键时序要求

| 时序参数 | 要求 | 原因 |
|---------|------|------|
| CS 低到首字节 | 无特殊要求 | 从机 DMA 已预先启动，硬件自动接收 |
| 帧间间隔 | ≥ 3ms (`SPI_INTER_FRAME_DELAY`) | 给 2800 执行 RX_DONE 处理 + 重启 DMA |
| 重传间隔 | 5ms (`SPI_RETRANSMIT_DELAY`) | 重传前给 2800 恢复时间 |
| DMA 重启完成时间 | < 下次 CS 低时间 | 否则下次传输数据丢失 |
| Bitmap ACK 超时 | 3s | 2N 侧 `wait_bitmap_ack` 的超时阈值 |
| SPI 整体超时 | 50s | 2800 侧 `cam_spi_timeout_timer` |
| 拍照超时 | 10s | 2800 侧 `cam_timeout_timer` |
| 最大重试次数 | 3 | 2N 侧 `max_attempts` |

## 4. 通信协议帧设计规范

> **协议演进**：系统经历了"每帧校验 → 窗口校验 → 末尾 Bitmap 汇总校验"三个阶段。当前采用**末尾 Bitmap 汇总校验**，2N 连续发送所有帧后，2800 用 bitmap 精确指示缺失帧，2N 仅重传缺失帧。详见 [SPI校验机制演进总结.md](file:///home/lzw/code/si8658ca/openvela_003_0623/openvela_si8658ca/doc/SPI校验机制演进总结.md)。

### 4.1 UART 协议帧格式

#### 4.1.1 帧结构

```
偏移   长度   字段          类型      说明
───────────────────────────────────────────────────────
0      2      SYNC         uint16    同步字: 0xAA 0x55
2      2      LEN          uint16    帧长度: CMD(1) + SEQ(1) + PAYLOAD(N) (大端)
4      1      CMD          uint8     命令码
5      1      SEQ          uint8     序列号 (当前固定为 0)
6      N      PAYLOAD      bytes     负载数据 (N = LEN - 2)
6+N    2      CRC16        uint16    CRC16-CCITT 校验 (大端, 覆盖 LEN ~ PAYLOAD)
```

**总长度** = 6 + LEN 字节

#### 4.1.2 命令码定义

| CMD 值 | 名称 | 方向 | Payload | 说明 |
|--------|------|------|---------|------|
| 0x01 | CAPTURE_REQ | 2800→2N | 空 | 请求拍照 |
| 0x02 | CAPTURE_ACK | 2N→2800 | filename[32] + thumb_w[2] + thumb_h[2] + thumb_size[4] | 拍照成功 |
| 0x03 | CAPTURE_FAIL | 2N→2800 | err_code[1] | 拍照失败 |
| 0x04 | GET_IMAGE_REQ | 2800→2N | 空 | 请求获取原图 |
| 0x05 | GET_IMAGE_ACK | 2N→2800 | filename[32] + file_size[4] | 原图信息 |
| 0x07 | SPI_READY | 2800→2N | session_id[4] | 2800 就绪，开始传缩略图 |
| 0x08 | FRAME_ACK | 2800→2N | 见 §4.1.3 Bitmap ACK 负载 | 帧确认（含 bitmap） |
| 0x09 | SPI_READY_BIG | 2800→2N | session_id[4] | 2800 就绪，开始传原图 |

#### 4.1.3 Bitmap ACK 负载格式（末尾汇总校验）

```
偏移   长度   字段          类型      说明
──────────────────────────────────────────
0      4      session_id    uint32    会话 ID (大端)
4      4      offset        uint32    已收数据最大偏移 (大端)
8      1      ok            uint8     1=全部收到，0=有缺失帧
9      2      nframes       uint16    总帧数 (大端)
11     bmp_len bitmap       bytes     每个 bit 对应一帧: 1=已收, 0=缺失
```

**bitmap 编码**：bit 0 对应 frame 0，bit 7 对应 frame 7，byte 1 bit 0 对应 frame 8。`bmp_len = (nframes + 7) / 8`。

### 4.2 SPI 协议帧格式

#### 4.2.1 帧结构

```
偏移   长度   字段          类型      说明
───────────────────────────────────────────────────────
0      4      MAGIC        uint32    魔数: 0x494D4731 ("IMG1") (大端)
4      1      TYPE         uint8     帧类型
5      4      SESSION_ID   uint32    会话 ID (大端)
9      4      TOTAL_LEN    uint32    图片总字节数 (大端)
13     4      OFFSET       uint32    本帧 payload 偏移 (大端)
17     2      DATA_LEN     uint16    payload 字节数 (大端, ≤256)
19     N      PAYLOAD      bytes     实际数据 (N = DATA_LEN, 最大 256)
19+N   2      CRC16        uint16    CRC16-CCITT (大端, 覆盖 MAGIC ~ PAYLOAD)
```

**最大帧长** = 19 + 256 + 2 = 277 字节

#### 4.2.2 帧类型定义

| TYPE 值 | 名称 | 说明 |
|---------|------|------|
| 1 | THUMB_DATA | 缩略图数据帧 |
| 2 | THUMB_END | 缩略图结束帧（payload 为空，触发 bitmap ACK） |
| 3 | BIG_DATA | 原图数据帧 |
| 4 | BIG_END | 原图结束帧 |

### 4.3 帧校验机制

- **校验算法**：CRC16-CCITT (多项式 0x1021，初始值 0xFFFF)
- **UART 帧校验范围**：LEN ~ PAYLOAD
- **SPI 帧校验范围**：MAGIC ~ PAYLOAD
- **校验失败处理**：
  - UART：丢弃当前帧，重新搜索同步字
  - SPI：`pos++` 跳过当前字节，靠 magic 重新对齐，等 END 帧汇总

### 4.4 末尾 Bitmap 汇总校验设计

#### 4.4.1 工作流程

```
2N: 发送所有数据帧 (frame 0 ~ N-1)
2N: 发送 END 帧
                         2800: 收到 END，遍历 bitmap
                         2800: 构建 bitmap ACK (ok + nframes + bitmap)
2N: 收到 bitmap ACK ◄── 2800: 发送 FRAME_ACK (bitmap)
  │
  ├─ if ok=1: 传输完成
  │
  └─ if ok=0: 解析 bitmap 找缺失帧
       2N: 仅重传缺失帧
       2N: 发送 END 帧
                           2800: 收到 END，再次遍历 bitmap
       2N: 收到 bitmap ACK ◄── 2800: 发送 FRAME_ACK
       ├─ if missing=0: 完成
       └─ else: 继续重试 (最多 3 次)
```

#### 4.4.2 优势分析

| 特性 | 每帧校验 | 末尾 Bitmap 汇总 |
|------|---------|-----------------|
| UART 交互次数 | N 次（每帧一次） | 1~3 次 |
| 1MB 大图传输时间 | ~9 分钟 | ~30 秒 |
| 重传效率 | Go-Back-N 整窗重传 | 选择性重传（仅缺失帧） |
| 实现复杂度 | 简单 | 中等（需维护 bitmap） |
| 流控 | 自然限速 | 靠帧间延时 + DMA 重启 |

### 5.1 SPI DMA 接收失败 (`dma_recv ret=-5`)

**现象**：
- 2800 串口日志：`[SPI-SLAVE-DBG] dmaexchange port=0 dma_recv ret=-5`
- `trans_len` 计算为垃圾值（如 -537950944）
- 2N 侧 bitmap ACK 超时，重试 3 次后失败
- 照片传输无法完成

**分析过程**：
1. 对比 2N 和 2800 串口日志时间戳，确认 2N 发送时 2800 DMA 状态异常
2. 检查 `schedule_transfer(RX_DONE)` 中的 `des_cur_addr`，发现为 `0x0`（无效）
3. 分析 `trans_len` 计算：`trans_len = (uint32_t)des_cur_addr - (uint32_t)rx_dma_buffer`，当 `des_cur_addr=0` 时结果为巨大无符号值
4. 发现原有代码 `trans_len <= 0` 判断对 `uint32_t` 类型无效（永远 >= 0）
5. 追踪 `spi_dmaexchange()` 的错误处理路径，发现 `hal_user_spi_dma_recv` 返回 -5（-EIO）时未复位 `is_rx_processing`
6. DMA 失败后状态残留，后续所有传输都失败

**定位方法**：
```
1. 串口日志搜索 "dma_recv ret=" → 确认 DMA 失败
2. 搜索 "trans_len=" 和 "des_cur=" → 确认 des_cur=0x0 导致 trans_len 下溢
3. 检查 spi_dmaexchange() 错误处理 → 确认未复位状态
4. 检查 trans_len 判断逻辑 → 发现 uint32_t <= 0 永远为 false
```

**解决方案**：
```c
// 1. 修正 des_cur_addr 有效性检查（替代无效的 trans_len <= 0）
if (des_cur_addr == 0 || des_cur_addr < (uint32_t)priv->rx_dma_buffer ||
    trans_len > priv->rx_dma_length) {
    // 错误恢复：close + reopen SPI 硬件
    hal_user_spi_stop_dma_recv(priv->port);
    hal_user_spi_close(priv->port, &priv->cfg);
    hal_user_spi_open(priv->port, &priv->cfg);
}

// 2. DMA 失败时复位状态 + 硬件重启
if (ret < 0) {
    priv->is_rx_processing = false;
    hal_user_spi_stop_dma_recv(priv->port);
    hal_user_spi_close(priv->port, &priv->cfg);
    hal_user_spi_open(priv->port, &priv->cfg);
}

// 3. spi_dmaexchange 增加 3 次重试
for (retry_cnt = 0; retry_cnt < 3; retry_cnt++) {
    ret = hal_user_spi_dma_recv(...);
    if (ret == 0) break;
    if (ret == -5 && retry_cnt < 2) up_mdelay(1);
}
```

**应用层配合**：`camera_page.c` 中 SPI 超时后调用 `cam_spi_reopen()`（close + 50ms + open），强制重新 bind 并重启 DMA。

### 5.2 连续传输丢数据（第一次完整，后续越来越少）

**现象**：
手动测试 `spi-pipe` 发送 `hello lubancat   `（18 字节），2800 用 `cat /dev/spislv0` 接收：
- 第 1 次：`hello lubancat   ` ✓（18 字节完整）
- 第 2 次：`hel`（仅 3 字节）
- 第 3 次：`h`（仅 1 字节）
- 之后：完全收不到

**分析过程**：
1. 在 `cs_irq_worker` 添加日志，观察 `is_rx_processing` 状态
2. 发现第 2 次传输时 `is_rx_processing=false`，说明 DMA 未启动
3. 分析 `schedule_transfer(RX_DONE)` 后的代码路径：
   ```c
   // RX_DONE 后...
   if (spislave_prepare_next_tx(dev) == 0) {   // 如果有 TX 数据，返回 0
       goto _exit;                              // 直接退出！跳过 spislave_prepare_next_rx！
   }
   // 下面的 spislave_prepare_next_rx 永远不会执行
   ```
4. 确认 `spislave_prepare_next_tx` 返回 0 时 `goto _exit`，跳过了 RX DMA 重启
5. 后续 CS 中断时 DMA 未就绪，2N 发送的数据被丢弃
6. 每次传输 DMA 启动越来越晚，导致接收数据越来越少

**定位方法**：
```
1. 手动测试: echo -n "hello lubancat   " | spi-pipe -d /dev/spidev3.0 -s 2000000
2. 2800 侧: cat /dev/spislv0
3. 观察每次接收字节数递减
4. 在 cs_irq_worker 添加日志: spiinfo("rx_proc=%d", priv->is_rx_processing)
5. 确认第二次传输时 rx_proc=false（DMA 未启动）
6. 检查 schedule_transfer(RX_DONE) 后的代码路径，发现 goto _exit 跳过 RX 重启
```

**解决方案**：
```c
// RX_DONE 后立即重启 DMA，不受 TX 路径影响
#if !defined(CONFIG_BES_SPISLAVE_ACTIVE_RX)
  if (!priv->is_rx_processing) {
    spislave_prepare_next_rx(priv);  // ★ 优先重启 RX
  }
#endif

  if (spislave_prepare_next_tx(dev) == 0) {
    goto _exit;
  }

// cs_irq_worker 增加 fallback
if (priv->is_rx_processing) {
    schedule_transfer(priv, RX_DONE);
} else {
    spislave_prepare_next_rx(priv);  // ★ fallback: DMA 未启动则重启
}
```

### 5.5 SPI NACK 重传失败（每帧校验阶段）

**现象**：
2N 日志：`[WARN] frame NACK at offset=0, retry 3`，`[ERROR] Thumbnail send failed`。

**分析过程**：
1. 检查 2800 日志发现 `[camera_page] SPI timeout fired`，说明 2800 未发送 FRAME_ACK
2. 2N 侧每个数据帧发送后等待 FRAME_ACK，超时则重试 3 次
3. 2800 侧 SPI RX 线程虽然收到数据，但没有发送 ACK 的逻辑
4. 根因：每帧校验机制下，UART 交互过于频繁（346 帧 × 3ms = ~1s 仅 UART 交互），且 2800 应用层未实现 ACK 发送

**定位方法**：
```
1. 2N 日志搜索 "NACK" → 确认 NACK 重试
2. 2800 日志搜索 "FRAME_ACK" → 确认未发送 ACK
3. 检查 camera_page.c 的 SPI RX 线程 → 确认无 ACK 发送逻辑
4. 分析每帧校验的 UART 开销 → 确认性能瓶颈
```

**解决方案**：改用**末尾 Bitmap 汇总校验**，详见 [SPI校验机制演进总结.md](file:///home/lzw/code/si8658ca/openvela_003_0623/openvela_si8658ca/doc/SPI校验机制演进总结.md)。

```c
// 2800 侧：收到 END 帧后统一发送 bitmap ACK
if (type == THUMB_END) {
    // 遍历 bitmap 检查完整性
    uint8_t thumb_ok = 1;
    for (uint16_t fi = 0; fi < cam_recv_nframes; fi++) {
        if (!(cam_recv_bitmap[fi >> 3] & (1 << (fi & 7)))) {
            thumb_ok = 0;
            break;
        }
    }
    // 构建 bitmap ACK payload
    uint16_t bmp_len = (cam_recv_nframes + 7) / 8;
    uint8_t *ack = malloc(11 + bmp_len);
    ack[0..3] = session_id;
    ack[4..7] = cam_thumb_offset;
    ack[8] = thumb_ok;
    ack[9..10] = cam_recv_nframes;
    memcpy(ack + 11, cam_recv_bitmap, bmp_len);
    cam_uart_send_frame(CAM_CMD_FRAME_ACK, ack, 11 + bmp_len);
}
```

### 5.6 IOMUX 配置错误导致 SPI 无信号

**现象**：
SPI 通信完全无数据，示波器测 SCLK/MOSI 无波形。

**分析过程**：
1. 用万用表确认 SPI 引脚物理连接正常
2. 用示波器测 SCLK 引脚，无时钟信号
3. 检查 `bes_spislave_initialize()` 中的 `bes_spi_pincontrol()` 调用
4. 发现 IOMUX 未将引脚配置为 SPI 功能，引脚处于默认 GPIO 模式

**IOMUX 概念**：IOMUX（I/O Multiplexer，I/O 多路复用器）是 SoC 内部的引脚切换矩阵。一个物理引脚可以映射到多种功能（GPIO/SPI/UART/I2C 等），通过 IOMUX 寄存器选择。BES2800BP 的 SPI 引脚（MOSI/MISO/SCLK/CS）需要通过 `hal_iomux_set_spi_slave()` 配置为 SPI 从机功能。

**定位方法**：
```
1. 万用表测引脚连通性 → 确认硬件连接正常
2. 示波器测 SCLK → 无波形，确认无 SPI 时钟
3. 检查 bes_spi_pincontrol() → 确认 IOMUX 配置函数被调用
4. 读取 IOMUX 寄存器 → 确认引脚未配置为 SPI 功能
```

**解决方案**：
```c
// hal_iomux_set_spi_slave() 配置引脚
// 引脚 32-35 配置为 SPI 从机功能
hal_iomux_set_spi_slave(port);
// 设置：function = SPI_SLAVE, drive_strength = 0xF, pull = NONE
```

### 5.7 LVGL UI 线程安全问题

**现象**：
SPI/UART 接收线程直接更新 UI 控件，导致 LVGL 崩溃或界面卡死。

**分析过程**：
1. LVGL 不是线程安全的，UI 操作必须在 LVGL 主线程（或持有 `lv_lock` 的线程）执行
2. SPI RX 线程和 UART RX 线程在后台运行，直接调用 `lv_label_set_text()` 会破坏 LVGL 内部状态
3. 崩溃堆栈指向 LVGL 内部链表操作

**定位方法**：
```
1. 崩溃堆栈分析 → 指向 lv_label_set_text 等 UI 函数
2. 确认崩溃发生在 SPI/UART RX 线程上下文
3. 查阅 LVGL 文档 → 确认非线程安全
```

**解决方案**：使用 `lv_async_call()` 将 UI 操作投递到 LVGL 主线程：
```c
// SPI RX 线程中
lv_async_call(cam_show_thumbnail_async_cb, NULL);

// 回调在 LVGL 主线程执行
static void cam_show_thumbnail_async_cb(void *data) {
    lv_lock();
    // 安全地更新 UI
    lv_image_set_src(cam_preview, &cam_thumb_dsc);
    lv_unlock();
}
```

### 5.8 SPI 设备打开失败后状态残留

**现象**：
SPI 超时后重新打开设备，但 DMA 仍未启动，后续传输全部失败。

**分析过程**：
1. `cam_spi_reopen()` 中 close 后立即 open，但内核 `spi_slave_close()` 的 `UNBIND` 可能未完成
2. `crefs` 引用计数未正确递减，导致下次 open 不触发 `bind`
3. DMA 硬件状态残留，`is_rx_processing` 保持 true

**定位方法**：
```
1. 串口日志搜索 "spislave_bind" → 确认 reopen 时未触发 bind
2. 检查 crefs 计数 → 确认未正确递减
3. 检查 is_rx_processing → 确认状态残留
```

**解决方案**：close 后增加 50ms 延时，确保内核完成 UNBIND：
```c
static void cam_spi_reopen(void) {
    close(cam_spi_fd);
    usleep(50000);  // 50ms 延时，等待内核 UNBIND 完成
    cam_spi_fd = open("/dev/spislv0", O_RDWR);  // 重新触发 bind + DMA 启动
}
```

### 5.9 缩略图 RGB565 字节序问题

**现象**：
2800 显示缩略图颜色异常（红蓝颠倒或花屏）。

**分析过程**：
1. 2N 生成 RGB565 时使用小端序（低字节在前）
2. LVGL 的 `LV_COLOR_FORMAT_RGB565` 期望的字节序与 2N 生成的不一致
3. 像素高低字节顺序导致颜色错乱

**定位方法**：
```
1. 用测试色（纯红/纯绿/纯蓝）生成缩略图
2. 2800 显示后观察颜色 → 红蓝颠倒
3. 对比 2N 和 LVGL 的 RGB565 字节序定义
```

**解决方案**：在 2N 侧生成时按 LVGL 期望的字节序打包：
```python
# RGB565: R5 G6 B5，按 LVGL 字节序打包
r5 = (r >> 3) & 0x1F
g6 = (g >> 2) & 0x3F
b5 = (b >> 3) & 0x1F
pixel = (r5 << 11) | (g6 << 5) | b5
# 按小端序写入（低字节在前）
data.append(pixel & 0xFF)
data.append((pixel >> 8) & 0xFF)
```

## 6. 总结

本文档详细记录了 BES2800BP 与 Lubancat 2N 双机通信系统的架构、流程、协议和调试过程。关键要点：

1. **双通道设计**：UART 传控制信令，SPI 传图像数据，各司其职
2. **DMA 预启动**：SPI 从机 DMA 在设备打开时即启动，无需等待业务触发
3. **末尾 Bitmap 汇总校验**：替代每帧校验，大幅减少 UART 交互，支持选择性重传
4. **CS 中断驱动**：从机靠 CS 上升沿中断感知传输结束，重启 DMA 接收下一帧
5. **分层架构**：应用层 → 核心驱动 → LHF → HAL → 硬件，职责清晰

调试中遇到的核心问题均与 **DMA 时序**（预启动、重启、错误恢复）和 **协议效率**（每帧校验 → 末尾汇总）相关，解决方案已固化到代码中。
