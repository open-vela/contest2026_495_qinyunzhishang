## 1. 功能概述

### 1.1 业务背景

在智能手表应用场景中，提供会议录音实时转写功能，将会议过程中的语音内容转换为文字输出到屏幕，便于用户在会后查阅会议记录。

### 1.2 功能特性

| 特性 | 说明 |
|------|------|
| 语音识别引擎 | 阿里云百炼 paraformer-realtime-v2 流式 ASR 模型 |
| 通信协议 | WebSocket over TLS（wss://dashscope.aliyuncs.com/api-ws/v1/inference）|
| 音频格式 | PCM 16kHz / 16bit / 单声道 |
| 交互方式 | 语音指令"开始会议"触发，按钮结束会议 |
| 输出形式 | 屏幕字幕实时显示，会议结束后输出完整转写内容 |
| 后续扩展 | 飞书云文档写入接口（规划中）|

### 1.3 用户操作流程

```
用户唤醒语音助手 → 说出"开始会议" → 跳转会议页面 → 录音中...
                          ↓
        点击"结束会议"按钮 → 上传音频至 ASR 服务器
                          ↓
             接收转写结果 → 屏幕显示完整字幕
                          ↓
                  左滑返回退出会议页
```

## 3. 核心技术要点

### 3.1 ASR 模型选择

**选用模型**：`paraformer-realtime-v2`（阿里云百炼流式语音识别）

**选择理由**：
- 支持中文实时转写
- 通过 WebSocket 流式上传，边上传边识别
- 适合会议场景的长时间录音

**通信协议**：
- 端点：`wss://dashscope.aliyuncs.com/api-ws/v1/inference`
- 认证：Bearer Token（DashScope API Key）
- 音频传输：WebSocket Binary Frame（原始 PCM）
- 任务控制：WebSocket Text Frame（JSON 协议）

### 3.2 音频参数规范

| 参数 | 值 | 说明 |
|------|------|------|
| 采样率 | 16000 Hz | ASR 模型要求 |
| 位深 | 16 bit | PCM 编码 |
| 声道 | 1（单声道）| 会议场景适用 |
| Chunk 大小 | 3200 字节 | 100ms 音频（16kHz×16bit×1ch×0.1s）|

### 3.3 WebSocket 协议实现

**自定义 WebSocket 帧实现**（因 NuttX 无现成 WebSocket 库）：

```c
#define WS_FIN_BIT          0x80
#define WS_OPCODE_TEXT      0x01
#define WS_OPCODE_BINARY    0x02
```

**帧格式**：
- 文本帧：发送 JSON 控制消息（run-task / finish-task）
- 二进制帧：发送原始 PCM 音频数据
- 客户端发送需加 mask，服务端发送无 mask

### 3.4 TLS 安全通信

使用 mbedtls 实现 TLS 加密：
- 证书验证（CA 证书内嵌）
- TLS 1.2 握手
- 加密数据传输

## 4. 工作流程

### 4.1 整体流程

```
[1] 用户唤醒 → 语音助手识别"开始会议"
        ↓
[2] 触发回调 → 跳转到会议页面
        ↓
[3] 会议页面初始化 → 创建 UI 元素 → 启动录音
        ↓
[4] 录音中 → 状态栏显示"会议录音中，请开始发言"
        ↓
[5] 用户点击"结束会议" → 停止录音 → 生成 WAV 文件
        ↓
[6] 启动 ASR 转写线程
    ├── 验证 WAV 文件
    ├── TLS 连接服务器
    ├── WebSocket 握手
    ├── 发送 run-task 启动转写
    ├── 流式上传 PCM 音频（1倍速实时节奏）
    ├── 同时接收转写结果（duplex 模式）
    ├── 发送 finish-task 结束转写
    └── 接收剩余结果直到 task-finished
        ↓
[7] 转写结果通过回调 → 实时更新到字幕区
        ↓
[8] 转写完成 → 状态栏显示"转写完成，左滑返回"
```

### 4.2 音频上传流程（关键）

```
┌─────────────────────────────────────────────┐
│         asr_send_audio_file 流程            │
├─────────────────────────────────────────────┤
│  1. 动态查找 WAV data chunk 偏移             │
│  2. 定位到 PCM 数据起始位置                  │
│  3. 循环读取 3200 字节 chunk                 │
│  4. 每发送一个 chunk：                       │
│     ├── asr_ws_send_binary() 发送 PCM       │
│     ├── usleep(100000) 1倍速节奏控制        │
│     └── select(20ms) 检查服务器响应          │
│  5. 收到响应则解析 sentence_id 和 text       │
│  6. 通过回调 cb(text, sid, user_data) 上报  │
│  7. 循环结束发送 finish-task                 │
└─────────────────────────────────────────────┘
```

### 4.3 字幕显示流程

```
ASR 返回 text → meeting_asr_on_result 回调
        ↓
   sentence_id < 0 ?  ─── 是 ──→ 丢弃（错误提示）
        ↓ 否
   meeting_page_update_asr_transcript(text)
        ↓
   首次调用？ ─── 是 ──→ 显示"记录到的会议如下："标题
        ↓
   长度检测：
   text_len >= old_len ?  ─── 是 ──→ 覆盖同一行（累积识别）
        ↓ 否                        ↓
   新建行（新句子）          更新 current_asr_text
        ↓
   滚动到最底部
```

```c

```

**关键点**：
- 必须验证 RIFF/WAVE magic
- chunk 长度为奇数时有 1 字节 padding
- 返回 `pos + 8`（跳过 chunk header）

### 5.2 WebSocket Binary Frame 发送

```c

     *   - len < 65536: 2 字节（126 标记）
     *   - len >= 65536: 8 字节（127 标记）
     */
    /* 客户端发送必须加 4 字节 mask key */
    /* 分块发送（1024 字节）避免栈溢出 */
}
```

### 5.3 Duplex 通信（发送音频 + 接收响应）

**问题**：单纯发送音频会导致 socket 缓冲区溢出，服务器响应无法接收。

**解决方案**：使用 `select` 实现半双工轮询。

```c
while (remaining > 0) {
    /* 1. 发送一个 chunk */
    asr_ws_send_binary(chunk, chunk_size);
    
    /* 2. 1倍速节奏控制（关键！）*/
    usleep(100000);  /* 100ms = 1倍速 */
    
    /* 3. select 检查服务器响应（20ms 超时）*/
    select(fd + 1, &readfds, NULL, NULL, &tv);
    if (FD_ISSET(fd, &readfds)) {
        /* 4. 读取并解析响应 */
        mbedtls_ssl_read(ssl, tmp, sizeof(tmp));
        asr_extract_sentence(tmp, &sid, text, sizeof(text));
        cb(text, sid, ud);  /* 回调上报 */
    }
}
```

### 5.4 字幕去重算法（长度检测）

**问题**：ASR 流式返回同一句子的累积结果，且会修正前面已识别的字（如"办"→"半"），导致前缀检测失败。

**解决方案**：用长度比较代替前缀检测。

```c
int is_continuation = 0;
if (current_asr_label && current_asr_text[0]) {
    size_t old_len = strlen(current_asr_text);
    size_t text_len = strlen(text);
    /* 新文本长度 >= 旧文本长度 → 同一句子的累积识别 */
    if (text_len >= old_len) {
        is_continuation = 1;
    }
}

if (is_continuation && current_asr_label) {
    lv_label_set_text(current_asr_label, msg);  /* 覆盖同一行 */
} else {
    current_asr_label = lv_label_create(meeting_chat_area);  /* 新建行 */
    /* ... */
}
```

**效果**：最终只显示最后一行（最完整的累积结果）。

### 5.5 错误提示隔离

**问题**：错误提示（如"未收到转写内容"）会污染字幕区。

**解决方案**：用 `sentence_id < 0` 标记非转写文本，在回调中过滤。

```c
/* meeting_asr.c: 错误提示用 -1 作为 sentence_id */
callback("[ASR] 录音文件无效", -1, user_data);

/* meeting_page.c: 过滤非转写文本 */
static void meeting_asr_on_result(const char *text, int sentence_id, void *user_data)
{
    if (sentence_id < 0) {
        return;  /* 错误提示不显示在字幕区 */
    }
    meeting_page_update_asr_transcript(text, sentence_id);
}
```

### 5.6 标题显示时机控制

**问题**：标题"记录到的会议如下："在会议进行中显示会误导用户。

**解决方案**：创建时隐藏，转写开始时才显示。

```c
/* 创建时隐藏 */
lv_obj_add_flag(chat_title_label, LV_OBJ_FLAG_HIDDEN);

/* 转写开始时显示 */
void meeting_page_update_asr_transcript(...)
{
    if (chat_title_label && lv_obj_has_flag(chat_title_label, LV_OBJ_FLAG_HIDDEN)) {
        lv_obj_clear_flag(chat_title_label, LV_OBJ_FLAG_HIDDEN);
    }
    /* ... */
}
```

## 6. 关键问题与解决方案

### 6.1 NO_VALID_AUDIO_ERROR（服务器拒绝音频）

| 项 | 内容 |
|----|------|
| **现象** | 服务器返回 `NO_VALID_AUDIO_ERROR` 错误 |
| **原因** | WAV 文件包含 LIST/INFO 元数据 chunk，硬编码 44 字节偏移把元数据当 PCM 上传 |
| **解决** | 实现 `asr_wav_find_data` 动态查找 data chunk 偏移 |
| **验证** | 诊断显示实际偏移为 46 而非 44 |

### 6.2 转写内容丢失（只显示结尾）

| 项 | 内容 |
|----|------|
| **现象** | 20-30 秒录音只转写出最后几句话 |
| **原因** | paraformer-realtime-v2 是流式 ASR，内部维护有限长度滑动窗口；全速上传导致前文被挤出窗口 |
| **解决** | 加入 `usleep(100000)` 1倍速实时节奏控制，让 ASR 滑动窗口完整覆盖整个录音 |
| **权衡** | 转写耗时与录音等长，但完整性 100% |

### 6.3 字幕重复输出

| 项 | 内容 |
|----|------|
| **现象** | 同一句话显示多行（"先帝创业未办..."、"先帝创业未半..."等5行重复）|
| **原因** | ASR 流式返回累积结果时会修正前面的字（"办"→"半"），前缀检测失败导致每步新建行 |
| **解决** | 改用长度检测：新文本长度 >= 旧文本长度则覆盖同一行，否则新建行 |
| **效果** | 最终只显示最后一行（最完整的累积结果）|

### 6.4 "开始会议"无法跳转

| 项 | 内容 |
|----|------|
| **现象** | 说"开始会议"后不跳转到会议页面 |
| **原因** | 触发回调后代码继续执行 `ai_page_show_user_message`，被当作普通对话处理 |
| **解决** | 在 `s_meeting_callback()` 后立即 `return`，阻止后续处理 |

### 6.5 Socket 缓冲区溢出

| 项 | 内容 |
|----|------|
| **现象** | 音频发送中途卡死或转写结果丢失 |
| **原因** | 单向发送音频导致 socket 缓冲区满，服务器响应无法接收 |
| **解决** | 使用 `select` 实现 duplex 轮询，发送同时读取服务器响应 |

### 6.6 错误提示污染字幕区

| 项 | 内容 |
|----|------|
| **现象** | 字幕区出现"[ASR] 未收到转写内容"等错误提示 |
| **原因** | 所有 callback 都被显示到字幕区 |
| **解决** | 用 `sentence_id < 0` 标记错误提示，在回调中过滤不显示 |

## 10. 转写进度条功能（v1.1 新增）

### 10.1 功能背景

**原始痛点**：会议结束点击"结束会议"后，转写过程需要等待数十秒至数分钟，期间屏幕无任何反馈，用户感知"卡死"。

**产品需求**（同事韩成成提出）：
1. 转写过程中显示进度条，让用户知道系统在工作
2. **关键约束**：进度条必须在"字幕全部显示完毕之后"才能跑满 100%，避免"进度满了但字幕还没出完"的违和感

### 10.2 技术方案

#### 10.2.1 总体架构

```
┌─────────────────────────────────────────────────┐
│              LVGL 主线程（UI 刷新）              │
│  ┌───────────────────────────────────────────┐  │
│  │ 进度条 / 字幕区 / 状态栏 / dispatch队列  │  │
│  └───────────────────────────────────────────┘  │
│                     ▲ dispatch_async              │
└─────────────────────┼─────────────────────────┘
                      │
┌─────────────────────┼─────────────────────────┐
│              ASR 后台线程（detach）             │
│  ┌───────────────────────────────────────────┐  │
│  │ asr_send_audio_file → progress_cb(0-90%) │  │
│  │ finish-task                              │  │
│  │ 接收循环 → progress_cb(92-99%)           │  │
│  │ task-finished → progress_cb(100%)        │  │
│  └───────────────────────────────────────────┘  │
└─────────────────────────────────────────────────┘
```

#### 10.2.2 双阶段进度设计（核心）

| 阶段 | 进度范围 | 计算依据 | 上限 |
|------|---------|---------|------|
| 阶段一：发送音频 | 0% → 90% | 已发送字节 / WAV data 总字节 | 90% |
| 阶段二：收尾接收 | 90% → 99% | 每收到一段字幕 +2% | 99% |
| 终点：任务完成 | 99% → 100% | 收到 task-finished 事件 | 100% |

**关键设计**：阶段二停在 99%，直到服务器返回 `task-finished` 才到 100%，保证"字幕披露结束 < 进度跑满"。

### 10.3 线程模型与唤醒保障（关键技术难点）

#### 10.3.1 问题背景

最初方案用 `pthread_join` 等待 ASR 线程退出后再启动 `wakeup_detector`，结果导致**用户喊"小Q"无法唤醒**。

#### 10.3.2 根因分析

```
原始失败流程：
  左滑退出 → unloaded_cb
           → pthread_join(ASR线程)  ← 阻塞主线程数十秒！
           → wakeup_detector_start()  ← 延迟启动，用户喊了也没人听
           → 用户感知"唤不醒小Q"  ❌
```

**关键认知**：
- ASR 线程只读 WAV 文件 + 网络上传，**不占用麦克风**
- `wakeup_detector` 使用独立的 **VAD source**（与麦克风无关）
- 两者**无任何资源竞争**，根本不需要等待 ASR 退出

#### 10.3.3 最终方案：detach 模式 + 无阻塞唤醒

```c
/* 线程创建：detach 模式，退出后自动回收 */
pthread_attr_setdetachstate(&attr, PTHREAD_CREATE_DETACHED);
pthread_create(&meeting_asr_thread, &attr, meeting_asr_thread_func, NULL);

/* unloaded_cb：无条件立即启动 wakeup */
if (meeting_asr_thread_running) {
    pthread_detach(meeting_asr_thread);  /* 兜底，确保已 detach */
    meeting_asr_thread_running = false;
}
wakeup_detector_start();      /* 立即启动！无阻塞 */
voice_assistant_start();
```

**兼容性踩坑**：
- `pthread_timedjoin_np` / `pthread_tryjoin_np` 是 GNU 扩展，**NuttX 不支持**，编译报错
- 最终改用纯 detach 方案，反而更简单更安全

### 10.4 UI 线程安全

所有从 ASR 线程更新 UI 的操作都通过 `lvgl_dispatch_async` 入队，由 LVGL 主线程消费：

| 回调函数 | 作用 | 线程 |
|---------|------|------|
| `meeting_asr_result_async_cb` | 显示字幕 | 主线程 |
| `meeting_asr_progress_async_cb` | 更新进度条 | 主线程 |
| `meeting_asr_done_async_cb` | 隐藏进度条 + 显示"转写完成" | 主线程 |
| `meeting_asr_error_async_cb` | 红色错误提示 | 主线程 |

**内存安全**：`strdup` 的内存在 dispatch 失败时立即 `free`，dispatch 成功时在主线程回调中 `free`。

### 10.5 完整执行时序

```
T=0s      点"结束会议" → 显示进度条(0%) + 创建ASR后台线程
T≈27s     发送完90%音频 → 进度=90%（停在这里）
T≈30s     发送完所有音频 → 进度仍=90%
          ↓ 发送 finish-task
T≈30.1s   进入接收循环
          ↓ 字幕1 → progress=92%
          ↓ 字幕2 → progress=94%
          ↓ ...
T≈34s     最后一段字幕显示 → progress=98-99%  ✅ 披露结束！
T≈35s     收到 task-finished → progress=100%  ✅ 此时才跑满
          ↓ 隐藏进度条 + 显示"转写完成"

用户随时左滑退出：
          → pthread_detach（兜底）
          → wakeup_detector_start()  ✅ 立即启动
          → 喊"小Q小Q" → 唤醒成功
```

### 10.6 关键问题与解决方案

| 序号 | 问题 | 解决方案 |
|------|------|---------|
| 1 | pthread_join 阻塞主线程导致唤醒失败 | 改用 detach 模式，unloaded_cb 中不 join |
| 2 | NuttX 不支持 pthread_tryjoin_np/timedjoin_np | 纯 detach 方案，仅用 POSIX 标准 API |
| 3 | 进度条跑满但字幕还没显示完 | 双阶段设计：90% 上限 + 99% 上限 + task-finished 才到 100% |
| 4 | ASR 线程退出时还在 dispatch 更新 UI | dispatch 回调全部 NULL 检查，页面销毁后安全跳过 |
| 5 | dispatch 队列满导致 strdup 内存泄漏 | dispatch 失败时立即 free |
| 6 | 进度条与"结束会议"按钮重叠 | 调整 alignment 为 `LV_ALIGN_BOTTOM_MID, 0, -82` |
| 7 | 重复点击"结束会议"创建多个线程 | `meeting_asr_thread_running` 标志防重复 |

### 10.7 文件改动清单

| 文件 | 改动内容 |
|------|---------|
| `meeting_asr.h` | 新增 `meeting_asr_progress_cb` 类型 + `progress_cb` 参数 |
| `meeting_asr.c` | 阶段一进度计算（发送字节占比，上限 90%）+ 阶段二进度（每段字幕 +2%，上限 99%）+ task-finished 到 100% |
| `meeting_page.c` | 进度条 UI 组件、后台 ASR 线程（detach 模式）、4 个 dispatch 回调、unloaded_cb 无阻塞唤醒、cleanup 双重保险 |

### 10.8 验证测试

| 场景 | 验证点 | 结果 |
|------|--------|------|
| 转写中左滑 → 喊小Q | 唤醒无阻塞 | ✅ 通过 |
| 转写完成左滑 → 喊小Q | 正常唤醒 | ✅ 通过 |
| 进度条 0→90→99→100 | 双阶段实时更新 | ✅ 通过 |
| 字幕在进度跑满前显示完 | 满足产品需求 | ✅ 通过 |
| 连续进出会议页面 3 次 | 无残留、无崩溃 | ✅ 通过 |
| 断网测试 | 红色错误提示 | ✅ 通过 |

### 10.9 经验总结

1. **资源依赖分析优先**：在引入线程同步机制前，先分析是否真的有资源竞争。本例中 ASR 读 WAV 与 VAD 唤醒使用独立资源，根本不需要 join。
2. **POSIX 标准 API 优先**：嵌入式 RTOS（如 NuttX）对 GNU 扩展支持不全，尽量用标准 API。
3. **UI 线程隔离**：后台线程绝不能直接调用 LVGL API，必须通过消息队列（dispatch）派发到主线程。
4. **进度条设计要符合用户感知**：技术上的"完成"和用户感知的"完成"可能不同步，要通过分阶段设计对齐。

## 11. 实时转录架构：方案B 边录边转（v2.0 新增）

### 11.1 功能背景与目标

**旧架构的痛点（v1.x：会后文件转录）**：会议结束后将 WAV 文件按 1 倍速上传云端转写（paraformer-realtime-v2 滑动窗口要求实时节奏），30 分钟会议需再等约 30 分钟才出字幕，用户全程面对无字幕的进度条。

**演进目标**：

| 目标 | 达成标准 |
|------|---------|
| 实时字幕 | 说话后 1-2 秒内上屏，会议结束即出完整内容 |
| 零内容缺失 | 开头 10 秒（连接建立期）音频完整补发转录 |
| 字幕连续 | 多句分行连续显示，不互相覆盖/清零 |
| 进度反馈 | 结束后 0-100% 渐进推进，反映真实阶段 |

### 11.2 双录音器架构（方案B核心）

NuttX media 框架允许同时 open 两个 `MEDIA_SOURCE_MIC` 实例（已经 `meeting_dual_recorder_test` 验证，脚本已退役删除）：

```
麦克风
  ├─ rec1: media_recorder 写 WAV 文件（合规存档，/emmc/audio/meeting_*.wav）
  └─ rec2: media_recorder 纯 PCM 读取（shm fifo，供 ASR 实时消费）

ASR 线程: media_recorder_read_data(rec2) → WebSocket Binary → 云端
```

rec2 失败时自动降级为 v1.x 文件转录路径（`meeting_asr_thread_func` 中 `recorder_handle == NULL` 分支）。

### 11.3 连接预热 + 积压补发（消灭开头 10s 丢失）

TLS+WS 握手需 3-8 秒，期间 rec2 的 shm fifo 仅约 **10112 字节 ≈ 316ms** 容量，直接等待必然溢出丢音。三层防御：

```
进入会议页 → 后台线程预握手 TLS+WS（s_warm_tls，互斥锁 s_warm_lock 保护）
点开始 → asr_stream_connect_wait:
  ├─ 预热完成 → 直接复用（0 等待）
  ├─ 预热线程握手中 → 等待循环：每轮 read_data 读 1 块(100ms)
  │   → 积压链表 asr_blk_t 暂存（上限 100 块 ≈ 10s）
  └─ 预热失败 → 冷连接（含重试）
连接就绪 → asr_backlog_send 追赶式补发积压音频
```

### 11.4 追赶式补发（防 fifo 二次溢出）

补发期间实时音频仍在流入 fifo。**不能全速狂发**（8s 积压 1-2s 发完，期间无人读 fifo → 溢出丢等待末段音频）。采用**发 2 读 1**：

- 连续不读 fifo 最长 ~30ms << 316ms 容量，不溢出
- 每轮净消耗 1 块 → 有限轮结束，无死循环
- fifo 空时 read_data 阻塞 ~100ms 充当限速器 → 约 2.5 倍速追赶
- 边读到的块追加到链表尾部 → 严格 FIFO，云端收到的音频无乱序

### 11.5 sentence_id 字幕分行

paraformer-realtime-v2 的 `result-generated` 事件携带 `sentence_id`：

- 同 sid = 同句累积/修正 → 覆盖同一 label 行内文本
- 不同 sid = 新句 → 新建 label 行（同时把上一句最终版追加进 `s_full_transcription` 供飞书纪要）
- sid 解析失败(-1) → 兜底退化为长度比较（即 v1.x 的 5.4 节算法）

### 11.6 帧合并排空（asr_drain_results）

突发补发后云端连发多帧结果，**TCP 会把多个 WebSocket 帧合并进一个 TLS 记录**。必须按 WS 帧边界逐帧读取排空，而非裸 `mbedtls_ssl_read` 一次读整段：

```
while (mbedtls 内部缓冲有数据 || select(0超时) 可读):
    asr_ws_recv_text()  ← 精确读一帧（解析帧头+长度）
    匹配 result-generated → 提取 sid+text → 回调
```

双重出口条件缺一不可：`mbedtls_ssl_get_bytes_avail()` 捕捉已解密进内部缓冲的帧，`select` 捕捉内核 socket 数据。

### 11.7 智能跟随滚动

字幕区仅约屏高 38%（1-2 行视野）。每句新建行后仅在用户位于底部时 `scroll_to_y(MAX)`（`lv_obj_get_scroll_bottom() <= 40` 判定）；用户上翻回看历史时不被拉回，滚回底部恢复跟随。检测必须在更新 label **之前**——新建行会立即改变滚动几何。

### 11.8 渐进式进度条

里程碑只抬升爬升上限 `cap`，从不直接设值；100ms 定时器 +1/tick 爬升：

| 里程碑 | 时机 | cap 抬升至 |
|--------|------|-----------|
| 0 | 点击结束（流式模式） | 28 |
| 30 | 转写收尾完成 | 38 |
| 40 | LLM 开始 | 68 |
| 70 | LLM 完成 | 88 |
| 90 | 飞书保存完成 | 98 |
| 100 | done（杀定时器+隐藏） | — |

"下一里程碑-2"保证爬升永不超前真实进度、无回跳。仅流式模式启用（rec2 句柄非空判定）；文件模式保留 v1.1 双阶段直设（10Hz 直设与爬升互斥会回跳抖动）。定时器在 done/重新开始/页面销毁三处删除。

### 11.9 线程模型与 UI 派发

沿用 v1.1 的 detach 模式（10.3 节）与 dispatch 派发（10.4 节），v2.0 补充：

- ASR 线程（32KB 栈，detach）只做网络 IO 与回调，**绝不直接碰 LVGL**
- 结果事件打包 `asr_result_msg_t{text, sid}` 堆分配派发，消除共享全局变量竞态
- rec2 的 close 由 ASR 线程自己收尾（避免 use-after-close）
- 预热连接的复用/废弃由 `s_warm_lock` 互斥锁同步（语言切换快速重启场景）

## 12. 踩坑实录（v2.0）

### 12.1 sentence_id 解析 off-by-one —— "每说一两句字幕清零"

- **现象**：字幕累计 1-2 行后自动清零重来；《静夜思》只显示最后一句，飞书纪要同样只剩末句
- **根因**：`strstr(json, "\"sentence_id\":")` 后 `sp += 13`——字面量实际 14 字符（含冒号），sp 停在冒号上，`atoi(":3")` 恒返 0 → **所有句子 sid 均为 0** → UI 把每句都判为"同句"互相覆盖
- **修复**：`sp += strlen("\"sentence_id\":")`，杜绝魔法数字
- **教训**：手写字面量偏移必须用 `strlen(字面量)` 表达，让编译器算；该 bug 潜伏已久，只因旧代码从未真正消费 sid 而未暴露

### 12.2 等长句误判 —— 长度比较的先天缺陷

- **现象**：《静夜思》四句各 5 字，等长 → 长度比较判为"同句"，互相覆盖丢失
- **修复**：改用云端 sentence_id 判定（坑 12.1 修复后才真正生效）；sid 缺失时保留长度比较兜底
- **教训**：启发式判定在边界输入（等长、ASR 修正变短）下必然翻车，优先使用协议自带的权威标识

### 12.3 补发期 fifo 溢出 —— 全速狂发的代价

- **现象**：补发机制上线后，前 10s 仍只有第一句"床前明月光"
- **根因**：全速补发 8s 积压耗时 1-2s，期间无人消费 rec2 fifo（容量仅 316ms）→ 溢出丢等待末段音频
- **修复**：追赶式补发（发 2 读 1，见 11.4 节）
- **教训**：嵌入式音频 fifo 容量以百毫秒计；任何"停止消费"的操作（全速发送、阻塞等待）都要对着 fifo 容量算时间预算

### 12.4 TCP 帧合并吞句 —— 裸 ssl_read 的隐形丢帧

- **现象**：坑 12.3 修复后仍只有第一句；实时流却从未丢句
- **根因**：裸 `mbedtls_ssl_read` 无视 WS 帧边界，突发补发后云端连发多帧被 TCP 合并成一整段，一次 read 拿 2-4 帧但 `strstr` 只提取**第一帧**的 text/sid，**其余整帧静默丢弃**。实时流帧稀疏（几百 ms 一帧）不合并，故不触发
- **修复**：`asr_drain_results` 按 WS 帧边界逐帧排空（见 11.6 节）
- **教训**：`strstr`+偏移的 JSON 解析只能处理"单帧单句"；帧边界必须由 WS 帧头协议维护。另：同一份 diff 曾重复应用导致变量重复定义——应用 diff 后务必 grep 检查残留

### 12.5 等待循环排空死循环

- **现象**：预读等待期整场卡死，停止后仅送出链表留存的最后 ~10s
- **根因**：录音持续时 `read_data` 永远有数据，`for(;;)` 连续排空永不退出，预热状态整场得不到检查
- **修复**：每轮只读 1 块；`read_data` 阻塞到凑满 3200 字节本身就是限速器
- **教训**：先弄清阻塞 IO 的精确语义（等凑满缓冲 vs 立即返回），再设计循环

### 12.6 asr_load_key 无 null 终止 —— HTTP 400

- **根因**：`fread` 后未补 `buf[fn]='\0'`，`strlen` 读到栈垃圾污染 API Key
- **教训**：fread 的长度语义与 C 字符串零终止语义之间的鸿沟，是嵌入式 C 最常见的低级错误源

### 12.7 音频通道释放竞态

- **现象**：进入会议页立即 start 录音失败（voice_assistant 的 TTS 通道异步释放未完成）
- **修复**：`voice_assistant_stop` 后固定延时 500ms 再开 recorder
- **教训**：跨模块资源释放多为异步；立即重用前要留释放窗口

### 12.8 进度条瞬跳

- **现象**：里程碑 30/40/70/90/100 全部 `LV_ANIM_OFF` 直设，阶段间隙纹丝不动
- **修复**：见 11.8 节。**注意**：文件模式 10Hz 直设百分比与爬升定时器互斥（会回跳抖动），故仅流式模式启用爬升

## 13. 经验总结与最佳实践（v2.0）

1. **协议解析**：手写 `strstr`+偏移解析 JSON 时，跳过长度一律 `strlen("字面量")` 表达；关键字段（sid）要有明确的"缺失"哨兵值(-1)与兜底路径
2. **WS over TLS 读取**：永远按帧读（`asr_ws_recv_text`），排空要双检（`mbedtls_ssl_get_bytes_avail` + `select(0超时)`）
3. **fifo 预算思维**：所有消费音频的代码路径，计算"最长连续不读时长"对照 fifo 容量（本项目 316ms）留 10 倍余量
4. **阻塞 IO 语义先行**：设计读循环前先确认 `read_data` 的凑满语义并利用其作节奏器，而不是叠加 sleep
5. **链表不变量**：`tail==NULL ⟺ head==NULL`，发送耗尽、错误路径、每块发出后三处同步维护
6. **UI 线程安全**：ASR/LLM 线程只派发事件包（malloc 堆结构），回调内 free；绝不共享可变全局
7. **验证方法论**：屏幕上"消失"的内容先查飞书纪要/日志判断是**数据丢失**还是**视野问题**（滚动/覆盖），两条排查路径完全不同
8. **修复后回归**：每修一个 bug 全链路推演受影响路径（sid 修复暴露 UI 滚动问题、补发修复暴露帧合并问题）——链式缺陷是常态，修到"现象消失"前不算完

## 16. 多语言支持扩展（v2.1 新增）

### 16.1 背景与调研结论

原实现 `language_hints` 硬编码为 `["zh","en"]`，仅支持中英双语。经官方文档调研 + 设备实测双重验证，`paraformer-realtime-v2` **原生支持 8 语种**，语言能力是模型自带的，客户端只需放开参数：

| 代码 | 语言 | 代码 | 语言 |
|------|------|------|------|
| zh | 中文（含方言） | ko | 韩语 |
| en | 英文 | de | 德语 |
| ja | 日语 | fr | 法语 |
| yue | 粤语 | ru | 俄语 |

关键机制结论：
- `language_hints` 是**覆盖式**参数（非追加）：设 `["ja"]` 后中文也按日语声学模型解码 → 近音错字（不是 bug，是机制）
- 不设置时模型自动检测；设置多语种集合时在**集合内**自动检测
- 单语 hints 解码空间最小、单语质量最佳；多语共存 hints 支持同场混说（zh,en,ja 三语共存已实测通过）

### 16.2 参数化语言配置机制

免烧录切换验证语言，全部由设备端文件驱动：

| 文件 | 作用 | 用法 |
|------|------|------|
| `/emmc/asr_lang_hints` | 语言代码（覆盖默认集） | `echo ja >` 单语收窄 / `echo zh,en,ja >` 多语 |
| `/emmc/asr_debug_raw` | RAW 帧调试日志开关 | `touch` 开 / `rm` 关（与语言配置解耦） |

实现要点（`asr_fill_lang_hints`，每场会议开始时调用）：
- 文件不存在 → 默认八语种全集，模型在集合内自动检测
- 内容仅保留字母数字与逗号，防止破坏 JSON 结构
- 每场会议启动打印生效语言集：`language_hints=[...] test_mode=N`——eMMC 配置残留当场可见（曾因残留导致重启后中文错字，见坑 16.5.2）
- RAW 日志与语言配置**解耦**：质量验证需最小干扰（日志刷屏疑似影响 WAV 写入）；排查乱码时开 RAW 区分"识别错误"还是"字体缺字"

### 16.3 八语种验证结果（2026-09 实测）

| 语种 | 字幕显示 | 识别质量 | 备注 |
|------|---------|---------|------|
| 中文 | ✅ | ✅ | 质量基线保持（宽 hints 下无回退） |
| 英语 | ✅ | ✅ | — |
| 日语 | ✅ | ✅ | 60s+ 连续朗读不卡死；zh,en,ja 三语共存同场验证通过 |
| 俄语 | ✅ | ✅ | MiSans 含西里尔字形 |
| 德语 | ✅ | ✅ | 拉丁字母，字形零风险 |

### 16.4 已知问题：韩语屏幕乱码（字体缺谚文）

- **现象**：韩语音频字幕显示矩形（□），但 LLM 归纳与飞书文档内容完全正确
- **根因**：ASR 输出正确韩文 UTF-8；设备字幕字体 `MiSans-Normal.ttf`（FreeType 动态加载，疑裁剪版）缺谚文（Hangul）字形
- **诊断方法**：`touch /emmc/asr_debug_raw` 开 RAW 日志 → RAW 帧显示正确韩文 → 确认渲染问题而非识别问题
- **修复方向**：替换含谚文字形的完整版 MiSans（字族设计覆盖韩文），**无需代码改动**
- **遗留**：UI 通用字体 `lv_font_simsun_16_cjk` 为编译进固件的位图字体、不含谚文且无法文件替换，韩语 UI 需将各页面统一到 FreeType 动态字体

### 16.5 踩坑实录（v2.1）

#### 16.5.1 WS 超大帧流错位 —— 日语 35s 卡死重启

- **现象**：日语连续朗读约 35s 后字幕停滞；点停止后进度条卡在 30%；数分钟后设备卡死自动重启
- **根因链**（日志 + 代码双重证据）：
  1. 日语连续无停顿 → VAD 不切句 → 同句持续累积，且 paraformer 同句每次重发**累积全文 + 全量 words 数组** → 单帧 JSON 超 4KB 结果缓冲
  2. 原实现 `plen >= cap` 只读帧头返回 EOVERFLOW，**数 KB 载荷残留** TLS 缓冲区
  3. 下次读取把残留载荷中段当新帧头解析 → **WebSocket 流错位**
  4. 错位后解析出伪长度，载荷读取循环 `WANT_READ` 无限 usleep 重试 → **ASR 线程永久阻塞**
  5. UI 线程等待 ASR 线程退出 → 界面卡死 → **看门狗复位**
- **修复**（分层防御）：
  1. 超大帧**部分保留**：读前 16KB 保 text 解析（event/sentence_id/text 均在帧首 ~300 字节内），跳过 words 数组尾部（帧膨胀元凶：每字一条时间戳）；字节流守恒 `keep + skip = plen`，流同步保持
  2. 帧头/扩展长度/载荷读取统一 `asr_ws_read_exact`（30s 上限：收尾等 task-finished 正常 1-5s，拥塞 WiFi 下 16KB 大帧分段 trickle 3s 会误杀）；丢帧 skip 限时 10s（容忍 TCP 重传）
  3. 结果缓冲 4KB→16KB **静态全局**（32KB 线程栈装不下）；drain 句子缓冲 256→512 与 `current_asr_text[512]` 对齐（日语 UTF-8 每字 3 字节）
  4. 64 位扩展长度（plen==127）全帧类型支持
- **教训**：固定缓冲 + "不消费就返回" = 协议流错位；任何阻塞循环必须有退出时限，否则看门狗复位是唯一结局

#### 16.5.2 eMMC 配置跨重启残留 —— 中文近音错字

- **现象**：设备重启后中文转录大量近音错字（非乱码）
- **根因**：日语测试写入的 `asr_lang_hints` 在 eMMC **掉电不丢**，重启后中文会议仍按 `["ja"]` 解码——日语声学模型听中文，产出近音汉字
- **修复**：删除文件恢复默认；并增加每场会议启动打印生效语言集，配置状态当场可见
- **教训**：设备持久化配置是"隐形状态"，跨会话/重启的存在感必须在关键路径可见（启动日志）

#### 16.5.3 diff 合并变量重定义 —— 坑 12.4 的重演

- 两轮 diff 先后应用时 `int idle` 在同作用域声明两次，GCC `redefinition` 编译错误
- 与坑 12.4"同一份 diff 重复应用"同源：**应用 diff 后必须 grep 检查残留**

### 16.6 经验总结（v2.1）

1. **多语言验证方法论三件套**：文件参数化（免烧录切换语言）+ RAW 日志（区分识别/字体问题）+ 启动日志（配置可见性）——日语、韩语两次乱码排查均靠此快速定位
2. **协议帧尺寸先算后收**：解析二进制协议前先估算最大帧；DashScope 结果帧的膨胀源是 words 数组，而 text 恒在帧首——部分保留策略因此成立
3. **超时分层**：收尾等待（30s）> 丢帧数据在途（10s）> 正常往返（1-5s）；快慢网络都要能活，线程最坏 30s 保证退出
4. **识别与渲染分治**：屏幕乱码 ≠ 识别错误；飞书/RAW 日志（服务端或明文）与屏幕（设备字体）是两条独立证据链，先分清再修
